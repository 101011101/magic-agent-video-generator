# PRD draft v3 — fewer gates, scene-first text blocking, seeds on demand

> DRAFT, not committed. Changes to docs/PRD.md proposed after the rrh4 runs. Evidence: across two rrh4 runs the question loop
> raised 14 questions; 11 were "where did X come from?" and all 11 were answered "it was always there" (the environment's first
> appearance had introduced them); 3 were "mentioned but never on screen". It found no real story holes (the editor's first
> read found the only 3). In the slides run, 36 of 57 tries so far failed on pose, expression or position.

## 1. Principle
Models write; code keeps the state. **One hard rule** decides whether a plan can be painted. Every other check is a
**warning**: shown on the page, never blocking, never retried.

## 2. IDs: identity only
- The ID table is `id, name, aliases`. Its job is to track identity, so every element can be sourced consistently.
- Positions are not IDs: they live in the text blocks (which spot an element is at).
- Removed from the ID table: role, kind, place, parent, inside. Classification there caused two bugs (places lost on
  re-solve; a character "inside" a bed). What is fixed or movable, and what is packed in what, comes from the text blocks.
- Kept: tagging in context (pronouns resolved per sentence), coverage (parser first, LLM for leftovers), stable IDs across
  solves, the ID-tagged story as the text blocking's input.
- Physical links (a room inside a house, one door seen from both sides) move to the asset bank, where they are used (§6).

## 2b. Screenplay, then storyboard (replaces the code-generated sentences)
The image editor was given sentences generated by code from the records ("Red appears at the clear bedside working space
(crouching…)"). They are right for the state manager and nearly useless as picture descriptions: no "she crawls out of the
belly", no screen direction (the wolf "running ahead" was drawn facing us). Films solve this in two layers:
1. **Screenplay (adaptation), one LLM call.** The story becomes scenes. Each has a heading (place, time; a new place or a cut
   starts a new scene) and action lines: present tense, only what the camera sees and hears, with direction of movement
   ("runs away from us toward the far bend"). Simultaneous actions become separate beats. Dialogue is kept. It is readable
   prose: the user can read and correct it before any keyframe exists.
2. **Storyboard, one LLM call per scene, in parallel.** Each scene becomes panels; a panel is one instant (any number of things
   may change in it) and is one keyframe. Choosing the moments is a creative judgement (where the light first breaks in),
   so it is the storyboard model's job, not the state manager's.

## 3. Panels (the text blocks)
1. Scenes come from the screenplay (§2b): a scene is continuous in place and time.
2. **The storyboard writes each scene's panels in parallel** (one LLM call per scene). Each panel (= one slide) states:
   - **what we see**: one or two vivid sentences of the moment, with screen direction; this is what the image edit uses;
   - **elements**: the IDs in the frame;
   - **lines**: the story lines it covers, quoted;
   - **changes**: what changes, moves written from → to (who goes from which spot to which, pose, expression, what is picked
     up or put down); the edit says "move the X already here from A to B; there is exactly one X";
   - **introductions**: for any element new to a continuous scene, the story line that introduces it.
3. Code joins the scenes in order and folds the blocks into the state table.

Expected: 5–6 small calls at once instead of one 30-step call at high effort (about 13 minutes of text blocking down to
2–3), and fewer broken rules because each call holds one scene.

## 4. The state manager: one hard rule
**Every element in a frame has a source**:
- it was in the previous frame of the same continuous scene; or
- it is introduced at the start of its scene (a new place or after a cut: automatic, no question); or
- its block names the story line that introduces it.

The introduced tag is yes/no with the introducing line. No subtypes (entering, carried, appearing): those describe state, not
sourcing. Everything else is a warning: spots that do not match an exit, placing something already there, carry-in details,
mentions never on screen.

Sourcing is unchanged: the base of a slide is the latest frame containing its environment; an element entering a frame comes
from the latest frame that contains it, else (first appearance ever) its seed or its text spec (§6).

## 5. Questions and the gate
- Questions come only from the hard rule: an element new to a continuous scene with no introducing line, or used before it is
  introduced. A scene start is never a question.
- Routing: a story hole (nothing in the story introduces it) goes to the editor; a block that left an introduction out goes to a
  text-blocking patch.
- **Gate (code):** for every slide, every element's source resolves (previous frame, scene start, introducing line, or
  first appearance). No open questions. Warnings never block.

## 6. Asset bank: seed only when needed
An element gets a seed sheet if any of these hold; otherwise its first appearance is drawn into its first frame from its text
spec, and from then on its latest frame is its reference.

| Condition | Decided by | LLM |
|---|---|---|
| 1. The user specified it (upload or explicit spec) | flag from the user input | no |
| 2. It has a confirmed physical link (room ⊂ house, the same door inside and out) | link check (propose, then check against the text) | existing calls |
| 3. Its first appearance failed (identity or spec check rejected it) | check result at run time → make a seed, retry that slide | no |

- Environments follow the same rule: an environment's first appearance is its plate, painted from its environment spec
  (layout) and whatever is introduced at its first frame.
- Optional, not proposed: one LLM call over all elements asking which demand exact details a generic drawing would miss.
  Condition 4 catches the same cases by measuring failures.

## 6b. Scene grids (replaces the per-keyframe edit chain)
Keyframes are made ONE SCENE AT A TIME: a single 4k image draws all of a scene's panels as cells of a storyboard grid, and
code crops the cells into frames. Consistency inside one image (character, light, props) is far better than a chain of edits,
and a scene costs one call (300 credits at 4k) instead of one per panel. Rules learned on the bakery runs:
- Image 1 is always the environment's plate (room and camera); image 2 the latest frame there (state); then one reference per
  element entering the scene. Building a grid from a cropped cell lost the room after one hop.
- Every cell: the plate's room from the plate's fixed camera; close-ups only when a panel asks for one (then the video treats
  it as a cut). A per-cell room check (same room? same camera?) rejects the grid once with the violations named.
- Grid layouts keep 16:9 cells (1, 2×2, 3×3). The model may draw a different layout, add black dividers, fill columns instead
  of rows, or decorate the border: crop by the layout actually drawn, find the occupied cells, take the first n in reading order.
- Heavy grids (4k, many references) can time out at the provider: fall back once to 2k with two references.
- Video per scene: one clip between each pair of consecutive keyframes (start frame → end frame), sound from the screenplay
  notes, stitched; any inconsistency between keyframes becomes a morph inside the clip, so the grid rules above matter most here.

## 7. Slides: retries only for real breaks
A frame is retried only for: a missing or duplicated character, a physically impossible picture, a re-painted picture (framing
gate), or a seed-worthy first-appearance failure (§6, condition 3). Pose, expression and position become notes on the page.
In rrh4, 36 of 57 tries so far failed on pose, expression or position alone.

## 8. Speed
- Text blocking per scene, in parallel (§3).
- A text-blocking draft that breaks the hard rule gets a patch, never a full rewrite.
- ID tagging: extract the table once from the whole story, then tag chunks in parallel against it (now: in story order).
- Try medium effort for text blocking and environment specs; keep it only if the hard rule still holds.

## 8b. Decided in review (not changed)
- Edits of edits are kept: the latest frame carries every change made to an element. No clean identity anchors for now.
- Off-screen changes, shots and camera angles, flashbacks and non-linear time: later. Make the story linear first.
- One slide = one instant of time; any number of things may change in it (the current cap of 2 changes is removed).
- Parallel ID tagging: one call builds the ID table from the whole story, then about 10 calls tag one chunk each against that
  fixed table, in parallel; a chunk call cannot invent an ID.
- Seed condition "container whose contents must show" is dropped (it was a hard-coded case).

## 9. Terms
- **Scene**: a stretch of the story continuous in place and time.
- **Screenplay**: the story as scenes of visual action lines and dialogue (adaptation).
- **Storyboard / panel**: a scene broken into instants; a panel is one keyframe (what we see, elements, lines, changes,
  introductions). Replaces "text block".
- **Introduced**: an element has a source for its first appearance in a scene (scene start, or an introducing line).
- **Seed**: a sheet made before an element's first frame; only under §6.
- **Warning**: a finding shown on the page that blocks nothing.

  accept; a scene studio for whole-scene variants. No image is kept without an accept.

  (`experiments/prompt-map.mjs <run>`).
- Findings from the bakery runs (illustrated and photoreal): consistency inside one grid is strong; breaks happen at scene
