Your questions

How is the state manager built? Is the metadata deterministic? Does it track the theoretical types, the transformations and the in-between data?

Partly. For the agent's trees, what exists now is a record of facts plus a simulator, not a solver like the film's state manager:

  • Deterministic, by code: every material and every output is measured with ffprobe and ffmpeg: kind, width × height and aspect, seconds, sound (none / silent / present), alpha and how much is kept. Same file, same facts.
  • By a model, cached: each material is described once by the vision model, against fixed questions: people and where they are, the main subject, words verbatim, the ground. It's cached by file hash, so it never changes for that file, but it is a model's answer.
  • Theoretical types: pre-flight predicts each step's output, written on the step as predicted. The rules are code, one per tool, describing what the tool and our executor actually do.
  • In-between data: every intermediate output is a file. Its measured facts are kept on the step (facts) and on the session asset. That's where each card's "on paper vs measured" comes from.
  • What it does not do yet: it doesn't choose anything. The planner model still writes the tree; the code only predicts and checks it afterwards.
How does the tree get goal types? Is it done by the model or by tool choice? How is it solved?

The goal kind (image, video, change, sound, answer) and the fields (size, length, style, words) come from the sheet model. The path is written in one go by the planner model. It gets the catalogue, which lists each tool's takes, makes, well, poorly and cannot as text, and is told to "reason in states". No code searches for a path. Code then does three things: picks each step's model by rule (lettering or faithful edits → qwen), patches a few known mistakes, and checks the result on paper. So the solving is the model's; the type rules sit beside it as a checker.

The transformation is technically a table in preflight.js. For example: image-to-video turns a picture into a clip of the grid length with no sound (we drop it). talking-photo turns a picture plus a sound into a clip of the sound's length. background-remove turns a picture into a transparent picture and drops lettering. The end of the chain is compared with the sheet's goal.

A03d: should it have been two edits? Would types have caught it?

Two qwen edits would be about 54 characters each, still past what qwen spells reliably. Each edit also redraws the whole picture, so errors compound. Your reasoning is the right model, though. If the image tool declared exact lettering: up to ~40 characters per line, the goal state had "every quoted string exact", and text-overlay declared exact lettering: any length, then a type solver would find that the image node can't carry the address. It would send the address to text-overlay and the short lines to qwen. That's the plan that now passes the address. Today that rule is prose in the planner prompt, not a type; making it one is the proposal below.

C15a: why was the sequencing broken if the tree runs on its own?

The tree did run on its own: outputs fed inputs by name, and no agent stepped in. The mistake was in the tree the planner wrote. It read "the first 5 seconds" as an edit range and spliced the untouched 5 seconds back on (trim → swap → trim → assemble). So the face reverts halfway and the clip is 10 s. The executor faithfully ran a wrong plan. A goal type would catch it: the sheet's range is 0–5 s, so the goal is a 5 s clip, and pre-flight predicts 10.1 s. Pre-flight doesn't read the sheet's range field yet; that's a one-line addition. Not rerun yet (video).

C15c: is it good now?

Not shown yet. The tool can now map two faces to two portraits (the C14b fix, also wired for video), so the catalogue no longer says "cannot". But C15c hasn't been rerun: it's a video swap of about 300 credits, and the ledger is near the cap.

C17a: is it because the tree isn't deterministic code?

No. The tree is deterministic: once written, it runs as code with no agent in between. The gap was the tool contract. The voice tool accepted a seconds setting and silently didn't honour it, and nothing compared the output with the setting. That's now fixed three ways: voice honours it, pre-flight predicts lengths, and the step check measures them.

B07a: is "passes by eye" good enough? The alternatives

qwen recolours convincingly, but it redraws the whole frame: about a 2% squeeze, and the parked car behind shifts. Two ways to keep the background exact, both made here by code from the same photo (5 credits for the cut-out):

My take: for a person, qwen's result is the best available, and a by-eye pass is the right bar. No free tool both recolours realistically and keeps the background pixel-exact. In type terms, image-edit declares "background: approximate" and the code recolour declares "background: exact, edit: crude"; no path reaches "realistic and exact". So the honest outcome is to state that limit and grade the background perceptually, not pixel-for-pixel. I'd change the B07a must-have to "nothing else visibly changed".
